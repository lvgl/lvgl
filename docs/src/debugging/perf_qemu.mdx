title: "QEMU Render Benchmark"
description: "Counts the instructions LVGL's software renderer executes, on emulated Cortex-M, RISC-V and Cortex-A targets, so that a change's cost can be measured instead of guessed."
---

## What it is

`scripts/perf_qemu` builds LVGL for a bare metal target, runs the benchmark demo and every
`lv_demo_render` scene inside QEMU, and reports how many instructions each one took. It
also compares every rendered scene against the reference images in
`tests/ref_imgs/draw/render`, so a change that makes rendering faster and wrong does not
look like a win.

It runs in CI on every pull request and reports the difference against `master`, and it
runs the same way on your own machine.

## Why instruction counts

QEMU runs with `-icount shift=0`, where one instruction is one nanosecond of virtual time.
The counts are therefore **deterministic and host independent**: the same revision gives
the same number on your laptop and on a CI runner, so any difference between two runs is a
real difference and not measurement noise. Wall clock timing on a loaded machine swings by
tens of percent and cannot answer "did this commit help".

The trade-off is that this counts **instructions, not cycles**. QEMU charges one cycle per
instruction and models no cache, wait states or branch predictor. So it *understates* a
change that removes memory traffic or branches, and *overstates* one that merely folds
several stores into a single instruction. Real hardware is still what settles a close call.

## Requirements

Docker, and nothing else. The toolchains, the emulators and GDB all live in one container
image, which `run.sh` pulls from GHCR the first time it is needed and reuses after that.
There is no toolchain to install and nothing to build: it is the same image CI runs, which
is what makes a local count comparable with the one in a pull request.

The pull is about 900 MB and happens once. `--build-image` builds the image from
`scripts/perf_qemu/Dockerfile` instead, which is only useful when changing the Dockerfile
itself; `run.sh` also falls back to that on its own if the image cannot be pulled.

## How to run it

```bash
scripts/perf_qemu/run.sh
```

That measures the current working tree on every target and colour format CI uses. The first
run pulls (or builds) the container image, which takes a few minutes; later runs do not.

Results, error images and the build tree go to `build/perf_qemu` unless `-o` says
otherwise, and `run.sh` prints that path when it starts and when it finishes. Everything
else runs inside the container, where the same directory is `/out`, so the paths CMake and
QEMU print all begin with `/out`.

To narrow it down while working on one kernel:

```bash
# one target, one suite, one colour format
scripts/perf_qemu/run.sh -t riscv32 -s render -f rgb565

# a colour format and an optimisation level CI does not measure
scripts/perf_qemu/run.sh -f rgb888 --opt Os
```

`-t`, `-f` and `-s` all take comma separated lists, so several of anything is a single run:

```bash
scripts/perf_qemu/run.sh -f rgb565,rgb888             # two colour formats
scripts/perf_qemu/run.sh -t cortex-m7,riscv32 -f l8   # two targets
```

`run.sh --help` lists everything. The four targets are `cortex-m7`, `cortex-m55`, `riscv32`
and `cortex-a53`; the colour formats are the nine directories under
`tests/ref_imgs/draw/render`; the optimisation level is `Os`, `O2` (the default, and what
CI measures) or `O3`.

## Measuring one scene

A `-s` entry can name a single scene, which is then the only one measured. That is the
quickest loop while working on one drawing path, since nothing else is rendered at all.

```bash
scripts/perf_qemu/run.sh -s render:fill            # both opacities of one render scene
scripts/perf_qemu/run.sh -s render:fill_opa_128    # only that opacity
scripts/perf_qemu/run.sh -s bench:moving_wallpaper # one benchmark scene
scripts/perf_qemu/run.sh -s bench:multiple_arcs,render:text
```

A render scene named without an `_opa_` suffix covers both opacities. Scene names are the
ones in the reports: lower case, with underscores instead of spaces. Both suites report
per-scene figures whether or not a scene was selected, so the names can be read off a full
run.

## Comparing against a baseline

A number on its own says little. `--base` adds the comparison:

```bash
# measure master once, then reuse that measurement on every later run
scripts/perf_qemu/run.sh --base master

# or point at result files saved from an earlier run, yours or someone else's
scripts/perf_qemu/run.sh --base ~/master-results
```

Given a revision, `run.sh` measures it in a git worktree of its own, stores the result under
the output directory and reuses it as long as that revision and the settings do not change,
so `master` is measured once and not again. Given a directory, it reads the
`results-<target>.json` files there.

The report names the two revisions, lists the totals and the biggest per-scene movers, and
says whether any scene now renders different bytes than the baseline.

## Debugging a run

Any single run can be stopped and handed to GDB:

```bash
scripts/perf_qemu/run.sh -t cortex-m7 -s render -f rgb565 --gdb
```

QEMU then waits before its first instruction, with the port published from the container, so
GDB runs on your machine:

```bash
gdb-multiarch -ex 'target remote :1234' <output>/build/cortex-m7-O2/render_rgb565.elf
```

`run.sh` prints the output directory and the exact command.

**To end a `--gdb` run, press Ctrl-A then X.** Ctrl-C and Ctrl-D do nothing: QEMU runs with
`-nographic`, which gives it the terminal, and Ctrl-A is its escape key. Ctrl-A then H lists
the other escapes. Killing the container from another shell works too.

`--shell` opens a shell in the container instead, which is where the container's own
`gdb-multiarch` and `objdump` are.

## Reading the reference comparison

For every scene the report gives the largest per-channel difference from the reference image
and how many pixels differ, at a tolerance of 0. Zero everywhere is the expected result: the
software renderer is integer arithmetic, so an emulated target produces the same bytes as
the host test suite does.

A non-zero figure means the rendering changed. That is legitimate when it was intended, so
it is reported rather than failed, and the rendered image is saved next to the report for
comparison. `--tolerance N` allows a per-channel difference of `N`, which is useful while
deliberately reworking a filter and misleading the rest of the time.

## What CI does with it

On a pull request the workflow measures that revision and compares it against the counts
`master` last published, then adds a "Render Performance" row to the pull request report
comment. On a push to `master` it measures and publishes the new baseline. Nothing needs to
be run by hand.

## Adding a target

`scripts/perf_qemu/harness/plat.h` is the whole porting layer: an instruction count, a
semihosting call and a small number formatter, with one branch per architecture. A new
target needs a branch there, a `targets/<name>/` directory holding `link.ld`, `target.h` and
a startup file, a branch in `cmake/toolchain.cmake`, and its QEMU command line in
`perf_qemu.py`.
